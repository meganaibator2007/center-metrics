# ADR-02. Клиент на React вместо серверных шаблонов Thymeleaf

| Поле | Содержание |
|---|---|
| Статус | Принято. Предложено 01.11.2026; 07.11.2026 по предложению Готовца В. способ поставки изменён с C на E |
| Автор | Рошинец В. |
| Что меняет | Заменяет в ADR-01 решение о формировании страниц на сервере, отменяет ASR-09. Модульный монолит (ASR-06) остаётся |

## Контекст

- На 01.11.2026 в ветке `dev` нет кода приложения.
- При Thymeleaf каждая страница требует контроллер на Java. Основной frontend-разработчик не знает Java, а опытный Java-разработчик в команде один, поэтому интерфейс ждёт серверную часть и работа не идёт параллельно.
- Впереди экраны с динамикой, которые трудно сделать на HTML-формах без JavaScript: редактор полей показателя (T-40) и дашборд (US-26).
- ADR-01 отклонил SPA по трём причинам: две сборки, нужен опытный JavaScript-разработчик, срок MVP 13.11.2026. Две сборки остаются, но они независимы: у клиента и у сервера свой Dockerfile, а запуск по-прежнему одной командой. Срок MVP установила сама команда; защита проекта назначена на 20.11.2026, объём MVP под неё сокращён. Опыта React в команде по-прежнему нет, этот риск принимается (см. минусы).
- Готов статический прототип из 17 экранов: он остаётся образцом интерфейса, стили переносятся без изменений.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Оставить Thymeleaf | Ничего не меняем, экраны почти готовы к переносу | Интерфейс зависит от контроллеров; динамику делать трудно |
| B. Thymeleaf, а React только на T-40 и US-26 | Минимальный риск | Два подхода к интерфейсу; основные экраны по-прежнему ждут контроллеры |
| C. Клиент на React внутри jar Spring Boot | Клиент и сервер работают параллельно по контракту; единый подход; один контейнер приложения | Экраны переписываются; сборка Java зависит от Node.js (Maven-плагин скачивает Node); сервер сам отдаёт `index.html` для маршрутов клиента; в команде нет опыта React |
| D. Клиент на React в отдельном контейнере, браузер обращается к серверу напрямую | Клиент обновляется отдельно от сервера | Два адреса: нужен CORS и настройка cookie сессии между адресами |
| E. Клиент на React в контейнере nginx, nginx пересылает `/api/` на сервер | Плюсы C; сборки независимы: серверу не нужен Node.js, клиенту не нужен Maven; адрес для браузера один, CORS не нужен; маршруты клиента отдаёт nginx | Третий контейнер и конфигурация nginx |

## Решение

Выбран вариант **E**. Интерфейс – клиентское приложение на React и TypeScript, сервер отдаёт данные через REST API в формате JSON.

Docker Compose поднимает три контейнера: `frontend` (nginx с собранным клиентом), `backend` (Spring Boot) и `db` (PostgreSQL). Браузер ходит только на `frontend`: nginx отдаёт файлы клиента и пересылает запросы `/api/` на `backend`. Для браузера это один сайт, поэтому сессия в cookie и CSRF работают без CORS. Наружу открыт только порт `frontend`.

Сначала (01.11) был выбран вариант C. 07.11 команда перешла на E: так серверу не нужен Node.js в сборке, а клиент собирается и проверяется без Maven.

Вход остаётся на сессиях Spring Security, JWT не используем. Контракт между клиентом и сервером фиксируется в `docs/api.md`, он заменяет `docs/pages.md`.

## Последствия

Плюсы:

- Клиент разрабатывается на заглушках и не ждёт сервер, сервер разрабатывается по контракту.
- REST-контроллеры заменяют шаблоны, серверная часть не занимается представлением.
- Появляется основа для редактора полей и дашборда.
- Модульность, транзакции и правила пакетов не меняются: пересчёт баллов по-прежнему идёт в одной транзакции с записью (ASR-03).

Минусы:

- 17 экранов переписываются на React.
- В команде нет опыта React, а ревьюить клиентский код почти некому. Часть проверок берут на себя TypeScript, oxlint и сборка в CI.
- Появляются новые инструменты: Node.js, npm, Vite.
- Нужно отдельно настроить CSRF для клиента.
- Третий контейнер: конфигурация nginx (`frontend/nginx/default.conf.template`) и порядок запуска в Docker Compose.
- Первая загрузка страницы тяжелее, чем при серверных шаблонах. Это проверяется нагрузочным тестом по NFR-01.

Что сохраняется из требований: NFR-15 (запуск одной командой), NFR-06 (403 на чужие данные проверяется на сервере), NFR-08 (файлы только через контроллер), NFR-10, NFR-11 и NFR-12 (скорость ввода, браузеры, контраст и подписи полей).
