# База данных

PostgreSQL 16. Схему меняют только миграции Flyway в `app/src/main/resources/db/migration`, Hibernate её только проверяет (`ddl-auto: validate`). Общие правила миграций — в [архитектуре](ARCHITECTURE.md#база-и-миграции). Основание модели — ТЗ «Система учёта показателей эффективности», разделы 11.1 и 11.2.

24 таблицы в восьми миграциях, у каждого пакета свои таблицы с префиксом:

| Миграция | Пакет | Таблицы |
|---|---|---|
| `V100__user_create_tables.sql` | user | `usr_department`, `usr_program`, `usr_user`, `usr_user_category`, `usr_user_program`, `usr_role_assignment`, `usr_user_permission`, `usr_employment_history` |
| `V200__indicator_create_tables.sql` | indicator | `ind_indicator`, `ind_indicator_version` |
| `V300__period_create_tables.sql` | period | `per_period` |
| `V400__achievement_create_tables.sql` | achievement | `ach_achievement`, `ach_participant`, `ach_evidence`, `ach_decision`, `ach_achievement_revision` |
| `V500__scoring_create_tables.sql` | scoring | `scr_accrual`, `scr_score`, `scr_period_snapshot` |
| `V700__measurement_create_tables.sql` | measurement | `msr_measurement`, `msr_decision` |
| `V800__audit_create_tables.sql` | audit | `aud_event` |

## Как устроена модель

**Единый реестр.** Достижение вносится один раз и связывается со всеми авторами, включая внешних. Оно относится к одному показателю и одному периоду, поэтому в итоги двух периодов не попадёт. Второй автор присоединяется к существующей записи.

**Редакции показателей.** Показатель — это постоянный код и категория. Балл, порядок начисления, цель и коэффициент лежат в редакции. Правка создаёт новую редакцию, а достижение хранит ссылку на ту, по которой считается. К периоду относится редакция, действующая на дату его начала.

**Маршрут у каждого достижения.** `DRAFT` → `ON_REVIEW` → `REVIEWED` → `APPROVED`. С проверки результат можно вернуть (`RETURNED`) или отклонить (`REJECTED`), утверждённый — отправить на пересмотр (`REVISION`). Решения пишутся в `ach_decision`, прежние редакции — в `ach_achievement_revision`.

**Баллы.** Доля участника `B × c × w / Σw` считается при сохранении и лежит в `ach_participant`. Начисление `scr_accrual` появляется только при утверждении директором и только у сотрудников: доли внешних авторов никому не перераспределяются. Итог сотрудника по показателю за период `S = min(M, Σ)` лежит в `scr_score`.

**Округление.** Точная доля хранится с шестью знаками, официальный балл — с двумя. Копейки распределяются методом наибольших остатков, поэтому сумма по всем авторам равна `B × c`. При равных остатках лишний цент достаётся участнику с меньшим `id`.

**Цели РОП — отдельный тип оценки.** Значение за период не достижение: новое значение за следующий период дублем не считается, а второе за тот же период — считается. Баллы по этим показателям не начисляются.

## Общие правила

| Что | Как сделано |
|---|---|
| Первичный ключ | `id BIGINT GENERATED BY DEFAULT AS IDENTITY`, в JPA `@GeneratedValue(strategy = IDENTITY)` |
| Таблицы-связки | составной первичный ключ: `usr_user_category`, `usr_user_program`, `usr_user_permission` |
| Перечисления (роль, статус, тип) | `VARCHAR` + `CHECK (... IN (...))`, в JPA `@Enumerated(EnumType.STRING)` |
| Даты и моменты | `DATE` → `LocalDate`, `TIMESTAMPTZ` → `Instant` |
| Баллы, коэффициенты, значения | `NUMERIC` → `BigDecimal`, арифметика только на сервере |
| Снимки, старые и новые данные | `JSONB`, в JPA `@JdbcTypeCode(SqlTypes.JSON)` |
| Связи между пакетами | только колонка с ID (`user_id`, `period_id`, `indicator_id`), без внешнего ключа; существование проверяет сервис другого пакета |
| Связи внутри пакета | обычный внешний ключ: `ind_indicator_version → ind_indicator`, `ach_participant → ach_achievement` |
| Удаление | сотрудники деактивируются, показатели и справочники уходят в архив, периоды закрываются; удалить можно только черновик достижения, его участники, документы и решения удаляются каскадом |
| `created_at`, `updated_at` | заполняет Hibernate: `@CreationTimestamp`, `@UpdateTimestamp` |
| Имена ограничений | `таблица_что_тип`: `_fk`, `_uk`, `_ck`, `_ex`, `_idx`. Имя видно в тексте ошибки базы |

## Таблицы

### usr_department, usr_program — оргструктура

`usr_department`: `name` (уникальное), `archived`. `usr_program`: `code` (уникальный), `name`, `top_it` (только дисциплины программы «топ-ИТ» учитываются в показателях, где нужна программа), `archived`.

### usr_user — сотрудники и учётные записи

Сотрудник и учётная запись — одна таблица, `id` и есть стабильный идентификатор сотрудника.

| Колонка | Тип | Что это |
|---|---|---|
| `external_id` | VARCHAR(50), уникальный, null | устойчивый ключ для повторного импорта |
| `login` | VARCHAR(50), уникальный | `a-z 0-9 . -`, 3–50 символов, только нижний регистр |
| `password_hash` | VARCHAR(100) | хеш BCrypt |
| `last_name`, `first_name`, `middle_name` | VARCHAR(100) | отчество может быть пустым |
| `department_id`, `manager_id` | BIGINT, FK, null | подразделение и руководитель |
| `position` | VARCHAR(100), null | должность |
| `active` | BOOLEAN | false — учётная запись деактивирована |
| `must_change_password` | BOOLEAN | пароль временный: выдан при создании, сбросе или импорте |
| `last_login_at` | TIMESTAMPTZ, null | последний вход |

### usr_user_category — категории оценки

`user_id`, `category` (`PPS`, `AUP`, `ROP`). Определяют, какие показатели применимы к человеку. Это не роли.

### usr_user_program — программы сотрудника

`user_id`, `program_id`. Область проверки РОП хранится отдельно: РОП одной программы может преподавать на другой.

### usr_role_assignment — роли

| Колонка | Тип | Что это |
|---|---|---|
| `user_id` | BIGINT, FK | |
| `role` | VARCHAR(20) | `EMPLOYEE`, `REVIEWER`, `DIRECTOR`, `ADMIN` |
| `program_id` | BIGINT, FK, null | область: обязательна у `REVIEWER`, пуста у остальных |
| `valid_from`, `valid_to` | DATE | закрытая строка остаётся историей совмещения ролей |
| `assigned_by` | BIGINT, FK, null | кто назначил |

Одна и та же действующая роль с той же областью у человека только одна.

### usr_user_permission — полномочия сверх роли

`user_id`, `permission`: `IMPORT` — загрузка XLSX в своей области, `ENTER_FOR_OTHERS` — ввод за другого, `AUP_SELF_ENTRY` — самостоятельный ввод сотрудником АУП.

### usr_employment_history — история переводов

`user_id`, `department_id`, `position`, `valid_from`, `valid_to`, `changed_by`. Текущая строка — та, где `valid_to` пусто, она у сотрудника одна.

### ind_indicator — показатели

`code` (уникальный: ППС-01, АУП-04, РОП-11), `category`, `archived`, `archived_at`.

### ach_participant — участники и доли

`achievement_id`, `user_id` или `external_name` (ровно одно из двух), `weight` (больше 0, по умолчанию 1), `share` (α = w / Σw), `points_exact` (не меньше четырёх знаков), `points` (официальный балл, два знака), `basis` (обоснование). Сотрудник в достижении один раз.

### ach_evidence — подтверждения

`achievement_id`, `doc_type`, `requisites`, файл (`original_name`, `content_type`, `size_bytes`, `storage_key`, `checksum_sha256` — все вместе) или `url`, `version_no` и `previous_id` (история версий), `scan_status` (`NOT_SCANNED`, `CLEAN`, `INFECTED`), `archived_at`, `uploaded_by`, `uploaded_at`. Допустимые форматы и размер задаются настройками приложения, а не схемой. Сам файл лежит на диске вне `static/` (папка `APP_STORAGE_DIR`).

### ach_decision — решения

`achievement_id`, `revision`, `action`, `actor_id`, `comment` (обязателен при `RETURNED`, `REJECTED`, `REVISION`), `decided_at`. Строки только добавляются.

### ach_achievement_revision — прежние редакции

`achievement_id`, `revision` (вместе уникальны), `data` (карточка, участники и документы в JSON), `created_by`, `created_at`. Строка появляется перед пересмотром и перед присоединением соавтора к проверенной или утверждённой записи.

### scr_accrual — начисления

| Колонка | Тип | Что это |
|---|---|---|
| `achievement_id`, `revision`, `user_id` | вместе уникальны | |
| `indicator_id`, `indicator_version_id`, `period_id` | BIGINT | |
| `base_points`, `coefficient`, `share` | NUMERIC | копия правила на момент расчёта |
| `points_exact`, `points`, `formula` | | результат и формула |
| `status` | VARCHAR(15) | `ACTIVE` — входит в итог, `SUPERSEDED` — заменено новой редакцией, `CANCELLED` — пересмотр закончился отклонением |
| `calculated_by`, `calculated_at` | | инициатор и дата перерасчёта |

Двух действующих начислений одному человеку по одному достижению быть не может. На время пересмотра прежнее начисление остаётся в итоге и заменяется, когда директор утвердит новую редакцию.

### scr_score — итоги

`user_id`, `period_id`, `indicator_id` (вместе уникальны), `indicator_version_id`, `accrual_count`, `total_points`, `max_points`, `score`, `calculated_by`, `calculated_at`. Правило `score = min(max_points, total_points)` закреплено ограничением, без максимума итог равен сумме.

### scr_period_snapshot — снимок при закрытии периода

`period_id`, `snapshot_no`, `user_id`, `indicator_id` (вместе уникальны), `indicator_version_id`, `accrual_count`, `score`, `taken_by`, `taken_at`. Если период переоткрыли и закрыли снова, появляется снимок со следующим номером.

### msr_measurement — значения целевых показателей

| Колонка | Тип | Что это |

### msr_decision — решения по значениям

`measurement_id`, `action`, `actor_id`, `comment`, `decided_at`. Проверка данных и итоговое решение директора — две отдельные строки.

### aud_event — журнал аудита

`occurred_at`, `actor_id` (null — действие системы), `actor_name` (ФИО на момент действия), `action`, `object_type`, `object_id`, `object_name`, `old_data`, `new_data`, `comment`. Строки только добавляются.

### imp_job, imp_row — импорт

`imp_job`: `type` (`EMPLOYEES`, `INDICATORS`, `MEASUREMENTS`, `ACHIEVEMENTS`), `file_name`, `status` (`VALIDATED`, `APPLIED`), кто и когда загрузил и применил. `imp_row`: `job_id`, `row_no` (вместе уникальны), `action` (`NEW`, `UPDATE`, `SKIP`, `ERROR`), `key` (устойчивый ключ сопоставления), `message` (обязателен при `ERROR`), `payload`.

## Что проверено

Миграции накатаны через Flyway 12.4 на PostgreSQL 16.15, 172 проверки из 172:

- ограничения отклоняют плохие данные: роль старой модели, РОП без программы, балльную редакцию с целью и целевую с баллом, пересечение редакций и семестров, возврат без причины, файл без контрольной суммы, участника без имени, итог больше максимума;
- тот же DOI того же вида не проходит, другой вид и URL проходят, после отклонения достижение можно внести заново;
- пример из ТЗ: 20 баллов на четырёх авторов, из них два внешних, сумма долей 20, сотрудникам 10;
- второе действующее начисление запрещено, прежняя версия сохраняется;
- значение цели за следующий период и по другой программе — не дубль, исправление идёт новой версией;
- при нулевом знаменателе факт не хранится;
- черновик удаляется вместе с участниками, документами и решениями;
- без `out-of-order: true` новая `V101` после применённой `V900` не накатывается, с ним — накатывается.

Распределение копеек методом наибольших остатков, запрет проверять своё и поиск похожих записей живут в сервисах и проверяются тестами пакетов.

## Что ещё решить

- Кто утверждает достижение, если автор или соавтор — сам директор: ТЗ запрещает самоутверждение, но другого утверждающего не называет.
- Может ли директор вернуть результат на доработку: в таблице 4.1 возвращает только РОП, в разделе 10 возврат есть и у директора. Контракт пока разрешает.
- Можно ли открывать периоды, которые накладываются: ТЗ не запрещает, но достижение относится только к одному из них.
- Достижение и его привязка к показателю (`Achievement` и `IndicatorResult` в ТЗ) объединены в одну таблицу. Исключение из раздела 5.2, когда одно достижение засчитывается по другому показателю, потребует отдельной таблицы, если такие исключения есть в методике.
- Нужна ли настоящая антивирусная проверка: колонка `scan_status` есть, сервис проверки не выбран.
