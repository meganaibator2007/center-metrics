# Технические соглашения

Проект: веб-система учёта показателей деятельности центра (center-metrics).
Статус: **черновик v0.2**, обсуждается командой. Пункты с пометкой «[согласовать]» требуют решения.
Ответственный: Рошинец В. (Team Lead). Изменения вносятся только через pull request.

## 1. Стек и версии

| Часть | Что используем |
|---|---|
| Язык | Java 25 (LTS) |
| Фреймворк | Spring Boot 4.1.x (последний патч; официально поддерживает Java 17–27): Web MVC, Security, Data JPA, Validation, Actuator |
| Интерфейс | React, TypeScript, Vite, React Router |
| Стили | один файл `main.css` с фирменными токенами брендбука, без CSS-фреймворков |
| Модули | Spring Modulith 2.x (версия, совместимая со Spring Boot 4.1) |
| Маппинг | ручные мапперы `XxxMapper` со статическими методами, без библиотек |
| БД | PostgreSQL 16 |
| Миграции | Flyway |
| Сборка | сервер – Maven (через `./mvnw`, версия Maven зафиксирована в wrapper): корневой `pom.xml` и модуль `app` (весь Java-код); клиент – npm и Vite в папке `frontend`, отдельно от Maven |
| Тесты | JUnit 5, Spring Boot Test, Testcontainers (PostgreSQL), JaCoCo |
| Стиль кода | Checkstyle (Java), oxlint (TypeScript) |
| Инфраструктура | Docker Compose (три контейнера: `frontend` на nginx, `backend`, `db`), GitHub Actions |

Интерфейс – клиентское приложение React, сервер отдаёт данные через REST API в формате JSON. Решение и альтернативы описаны в [ADR-02](adr/ADR-02-react-client.md).

## 2. Архитектура: модульный монолит

Одно приложение Spring Boot, разделённое на пакеты по фичам. Каждый пакет – будущий кандидат на выделение в отдельный сервис.

```
ru.fa.kpi
├── KpiApplication.java
├── common/       SecurityConfig, обработка ошибок, общие утилиты
├── user/         пользователи, роли, вход, смена пароля          (E3)
├── indicator/    категории, показатели, схема полей формы         (E4)
├── period/       отчётные периоды, закрытие                       (E5)
├── entry/        записи преподавателя, значения, файлы            (E6)
├── scoring/      расчёт баллов, суммы по показателю и периоду     (E7)
└── report/       статусы отчёта, отчёты, экспорт, контроль, дашборд (E8, E9)
```

### 2.1 Что лежит в пакете

Пакет – это **агрегат**: главная сущность и всё, что без неё не живёт (`Category` лежит в `indicator`, `Attachment` – в `entry`).

| Файл | Назначение | Видимость |
|---|---|---|
| `User` | JPA-сущность | package-private, где возможно |
| `UserRepository` | Spring Data JPA | package-private |
| `UserMapper` | ручной маппер: Request → Entity → Dto | package-private |
| `UserController` | REST API пакета: принимает запросы, отдаёт JSON | package-private |
| `UserRequest` | тело запроса + аннотации валидации | package-private |
| `UserDto` | данные для ответа API и других пакетов (record) | **public** |
| `UserService` | бизнес-логика, транзакции – API пакета | **public** |

Если в пакете больше ~15 файлов, допускается подпакет (например, `entry/attachment`).

Маппер пишется руками: статические методы `toDto(User)`, `toEntity(UserRequest)`, `update(User, UserRequest)`. Поля переносятся явно, по одному. `id`, роль, пароль и статус из запроса не копируются никогда, их задаёт сервис. DTO — `record`, поэтому новое поле не забудется: без него не соберётся вызов конструктора.

### 2.2 Правила зависимостей

1. Внутри пакета: `Controller → Service → Repository`. Контроллер не обращается к репозиторию и не содержит бизнес-логики.
2. Между пакетами – **только** через `XxxService` и `XxxDto`. Чужие сущности, репозитории и мапперы использовать запрещено.
3. Циклические зависимости между пакетами запрещены. Если пакету B нужно отреагировать на действие в A, A публикует событие, B его слушает.
4. Правила проверяет тест Spring Modulith `ApplicationModules.of(KpiApplication.class).verify()`, он запускается в CI.

Граф зависимостей:

```
user   indicator   period            ← ни от кого не зависят
  ↑        ↑         ↑
  └────── entry ─────┘               ← проверяет: период открыт, схема полей, отчёт не отправлен
            │ событие EntrySaved
            ▼
         scoring → indicator
            ↑
report → user, period, indicator, scoring, entry
   │ события ReportSubmitted / ReportReturned
   ▼
 entry блокирует / разблокирует редактирование
```

### 2.3 События

- Пересчёт баллов (`EntrySaved` → `scoring`) – **синхронный** `@EventListener` в той же транзакции: баллы должны обновляться сразу после сохранения (US-19).
- Некритичные реакции (журнал, уведомления) – асинхронный `@ApplicationModuleListener`.
- В событиях передаём только ID и простые значения, не сущности.

## 3. Интерфейс (React)

### 3.1 Как устроен запрос

```
браузер → экран React → GET /api/users → nginx → UserController → UserService → UserDto
        → JSON в браузер → React показывает таблицу
```

Все адреса API начинаются с `/api`: nginx пересылает их на сервер. Остальные адреса nginx отдаёт как `index.html`, дальше экран выбирает React Router.

Ошибки возвращаются в едином формате `ProblemDetail`: `400` с ошибками по полям, `401`, `403`, `404`, `409`. Клиент показывает ошибку под полем или сообщением на экране.

### 3.2 Структура кода

```
frontend/
├── package.json
├── public/                  шрифты и изображения
└── src/
    ├── main.tsx             точка входа, маршруты
    ├── api/                 запросы к серверу: один файл на пакет (user.ts, entry.ts)
    ├── components/          общие компоненты: Button, Field, Table, Alert
    ├── layout/              шапка, меню, подвал
    ├── pages/<пакет>/       экраны, например user/UserListPage.tsx
    └── styles/main.css      все стили проекта
```

Папки в `pages/` повторяют пакеты сервера. Миграции Flyway лежат в `app/src/main/resources/db/migration`.

### 3.3 Сборка и запуск

- Клиент и сервер собираются отдельно: сервер – `./mvnw package` (jar без клиента), клиент – `npm run build` в папке `frontend` (результат в `dist`). Сборке сервера не нужен Node.js, сборке клиента не нужен Maven.
- Docker Compose поднимает три контейнера: `frontend` (nginx), `backend` (Spring Boot) и `db` (PostgreSQL 16). Каждый образ собирается внутри Docker в два этапа, поэтому на чистом компьютере хватает `docker compose up --build` (NFR-15).
- Браузер ходит только на `frontend`. nginx отдаёт файлы клиента, для маршрутов клиента (`/cabinet`, `/admin/users`) отдаёт `index.html`, а запросы `/api/` пересылает на `backend:8080`. Адрес у браузера один, поэтому CORS не нужен, cookie сессии и CSRF работают без дополнительной настройки. Наружу открыт только порт `frontend`. Конфигурация nginx – `frontend/nginx/default.conf.template`, адрес сервера задаёт переменная `BACKEND_URL`.
- При разработке клиента: `npm run dev`. Vite перенаправляет `/api` на `localhost:8080`.
- Пока метода API нет, клиент работает на заглушках в `src/api`. Формат заглушки совпадает с `docs/api.md`.

### 3.4 Правила клиентского кода

- Только функциональные компоненты и TypeScript. Тип `any` запрещён.
- `dangerouslySetInnerHTML` запрещён (XSS).
- Запросы к серверу – только через `src/api`, не из компонентов напрямую.
- У каждого поля есть `<label>` и вывод ошибки от сервера.
- Без `style={...}`: все стили в `main.css`.
- Сортировка и фильтры хранятся в параметрах адреса (`?sort=score`), чтобы ссылку можно было отправить.
- Скрытие кнопки по роли – это удобство, **не защита**. Права проверяются на сервере.
- Новая библиотека добавляется только через PR с обоснованием.

### 3.5 Контракт между клиентом и сервером

Для каждого экрана в файле `docs/api.md` фиксируется, какие запросы он делает и что получает:

| Экран | Маршрут | Запрос | Ответ |
|---|---|---|---|
| Пользователи | /admin/users | GET /api/users?q= | список UserDto (id, fullName, role, active) |

Таблица заполняется по прототипу до начала разработки экрана. Изменение запроса или ответа – только вместе с правкой `docs/api.md`.

## 4. База данных и миграции

- Схема меняется **только** миграциями Flyway. `spring.jpa.hibernate.ddl-auto=validate`.
- Имя файла: `V<номер>__<пакет>_<что_делает>.sql`, между номером и описанием два подчёркивания. У каждого пакета свой диапазон номеров: user 100–199, indicator 200–299, period 300–399, entry 400–499, scoring 500–599, report 600–699. Например, `V400__entry_create_tables.sql`, следующая миграция пакета — `V401__entry_add_comment.sql`.
- Из-за диапазонов новая миграция может получить номер меньше уже применённой (`V101` после `V600`), поэтому включено `spring.flyway.out-of-order: true`.
- **Применённую миграцию не редактируем никогда.** Нужна правка – пишем новую миграцию.
- Таблицы с префиксом пакета: `usr_`, `ind_`, `per_`, `ent_`, `scr_`, `rep_`.
- Между пакетами храним только ID, без внешних ключей и без JOIN в коде.
- Индексы создаются в той же миграции, что и таблица; обязательно на `(teacher_id, period_id)` для записей и баллов.
- Поля формы показателя – колонка `jsonb`, схема полей хранится у показателя (ASR-01).
- Тестовые данные (T-17) – отдельные миграции в `db/seed`, подключаются только в профиле `dev`.

## 5. Безопасность

- Spring Security, вход через `POST /api/auth/login`, сессия в cookie с флагом `HttpOnly`; пароли – BCrypt. JWT не используем: сессию проще отозвать, а токен не приходится хранить в браузере.
- CSRF-защита включена: токен приходит в cookie, клиент передаёт его в заголовке запроса.
- Каждый метод API проверяет роль; доступ к данным другого преподавателя → 403 (NFR-06). На это пишется автотест.
- Загруженные файлы хранятся вне `static/` и выдаются через контроллер с проверкой прав (NFR-08).
- Репозиторий **публичный**: `.env`, пароли и ключи не коммитим. В репозитории лежит только `.env.example`.

## 6. Тестирование

| Что | Чем | Требование |
|---|---|---|
| Расчёт баллов (`scoring`) | юнит-тесты JUnit 5 на 5 эталонных примерах | покрытие ≥ 80 % (JaCoCo) |
| REST-контроллеры | `@WebMvcTest` | обязательно проверка 403 на чужие данные |
| Репозитории | `@DataJpaTest` + Testcontainers PostgreSQL | для запросов с JSONB |
| Границы пакетов | Spring Modulith `verify()` | в CI |
| Клиент | проверка типов TypeScript, oxlint, сборка Vite | в CI |

Юнит-тесты пишет автор кода. Ручное тестирование по тест-кейсам – Черенков С.

## 7. Стиль кода

- Checkstyle в CI, конфигурация лежит в репозитории [согласовать: Google Java Style с отступом 4].
- oxlint в CI для TypeScript, конфигурация `frontend/.oxlintrc.json` лежит в репозитории.
- Классы – существительные (`UserService`), методы – глаголы (`createUser`). Компоненты React – с большой буквы (`UserListPage`).
- Комментарии и сообщения пользователю – на русском, имена в коде – на английском.
- Lombok допускается для `@Getter`, `@Setter`, `@RequiredArgsConstructor`; `@Data` на JPA-сущностях не используем.

## 8. Работа с Git

### 8.1 Ветки

| Ветка | Назначение |
|---|---|
| `main` | стабильная версия: сюда попадает только готовый этап, одним PR из `dev`, с тегом версии (MVP – `v1.0.0`, в `main` до защиты 19.11) |
| `dev` | ветка текущего этапа: создаётся от `main`, в неё вливаются все PR этапа. После слияния этапа в `main` удаляется и создаётся заново от `main` |
| `backend-first-stage` | ветка задач сервера на этап MVP (Готовец В., Калинкин И.): создана от `dev`, в неё вливаются PR задач сервера. Сливается в `dev` на каждой контрольной точке, после 16.11 удаляется |
| `feature/T-07-layout` | работа над задачей: ветка от `dev` (задачи сервера – от `backend-first-stage`), номер задачи + 1–3 слова |
| `fix/BUG-12-login-error` | исправление дефекта, ветка от `dev` (дефект сервера до 16.11 – от `backend-first-stage`) |

Прямой push в `main`, `dev` и `backend-first-stage` запрещён.

Правила для `backend-first-stage`, чтобы в конце не было одного огромного PR перед заморозкой:

1. Ветка сливается в `dev` на каждой контрольной точке: 09.11 – вход через API, 12.11 – запись → балл, 16.11 – всё MVP.
2. PR из `backend-first-stage` в `dev` вливается обычным слиянием (Create a merge commit), не Squash: иначе git не видит, что изменения уже в `dev`, и следующая точка приносит конфликты.
3. После каждого слияния в `backend-first-stage` подтягивают `dev` (merge `dev` → `backend-first-stage`): там клиент, без него не проверить Docker Compose целиком.
4. После 16.11 задачи сервера идут в `dev` по общим правилам, `backend-first-stage` удаляется.

Перед удалением `dev` ветку по умолчанию в настройках репозитория переключают на `main`, а открытые PR этапа вливают или переводят на новую `dev`. Правило защиты привязано к имени ветки, поэтому для новой `dev` оно сохраняется.

### 8.2 Коммиты

Формат: `T-07: добавлен общий layout`. Один коммит – одно логическое изменение.

### 8.3 Pull request

1. PR открывается в `dev` (задачи сервера – в `backend-first-stage`), заполняется по шаблону.
2. В описании `Refs #<номер issue>` – **не** `Closes`: после слияния задача идёт в Testing, а не сразу в Done.
3. Нужно 1 одобрение и зелёный CI.
4. Ревьюеры:
   - PR в `dev` – Рошинец В. (клиент, CSS, структура); PR Рошинца В. – Готовец В. (соответствие `docs/api.md` и зелёный CI);
   - PR в `backend-first-stage` – Готовец В.; PR самого Готовца В. – Рошинец В.;
   - PR из `backend-first-stage` в `dev` – Рошинец В.: клиент работает с новыми методами API.
5. Срок ревью – 1 рабочий день.
6. Слияние – Squash and merge, ветка после слияния удаляется. Исключение – PR из `backend-first-stage` в `dev` (см. 8.1).

## 10. Производительность и кэширование

- Внешний кэш (Redis) не используем. Баллы материализуются при сохранении (ASR-03) – это основной «кэш».
- При необходимости – Spring Cache на Caffeine только для справочников: показатели, схемы полей, категории, текущий период. Кэшируем DTO, сбрасываем после коммита.
- Не кэшируем баллы, записи, отчёты и любые данные, зависящие от пользователя.
- Сначала измеряем (нагрузочный тест), потом оптимизируем: индексы и устранение N+1 важнее кэша.
- Статика (JS, CSS, шрифты) отдаётся с хешем в имени файла и долгим `Cache-Control`; ответы API с персональными данными – `no-store` (настройка Spring Security по умолчанию).
